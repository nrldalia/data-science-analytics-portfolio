# Four-retailer store import demo

All retailers, store names, lot numbers, streets and contact addresses here are
**synthetic**. Malaysian city/state names provide geographic context, but these
are not real business locations. Email addresses use the reserved `example.com`
domain. No database is seeded and no email is sent by generating these files.

## Demo structure

Import each file into its own retailer, not all four into one retailer.

| Retailer name | Retailer key | Service type | Import file | Stores |
|---|---|---|---|---:|
| Aurora Demo Grocer | `DEMO_AURORA` | SM | `demo_aurora_stores.csv` | 300 |
| Bayu Demo Hypermarket | `DEMO_BAYU` | HM | `demo_bayu_stores.csv` | 300 |
| Cempaka Demo Market | `DEMO_CEMPAKA` | MM | `demo_cempaka_stores.csv` | 300 |
| Damai Demo Retail | `DEMO_DAMAI` | SM | `demo_damai_stores.csv` | 300 |

Use these exact email fields when creating the four saved retailer setups:

| Retailer key | Sender email | Retailer email |
|---|---|---|
| `DEMO_AURORA` | `dataflow.aurora@example.com` | `retailer.aurora@example.com` |
| `DEMO_BAYU` | `dataflow.bayu@example.com` | `retailer.bayu@example.com` |
| `DEMO_CEMPAKA` | `dataflow.cempaka@example.com` | `retailer.cempaka@example.com` |
| `DEMO_DAMAI` | `dataflow.damai@example.com` | `retailer.damai@example.com` |

Each retailer has **285 Active stores, 15 Inactive stores, and 12 stores flagged
as exceptions**. The total is **4 retailers and 1,200 stores**. These are deliberate
demo proportions, not observed market statistics. Each retailer has 25 stores
assigned to each of 12 Malaysian city/state pairs for repeatable filtering.

Store IDs are `DEMO_<RETAILER>-001` through `DEMO_<RETAILER>-300`.
`retailers.json` contains retailer setup values, file associations, SHA-256
fingerprints of the CSV fixtures, counts and expected validation outcomes.

## Import columns

| Column | Meaning | Example |
|---|---|---|
| `store_id` | Retailer's stable store key; duplicates are matched case-insensitively | `DEMO_AURORA-001` |
| `store_name` | Human-readable store name | `Aurora Demo Kuala Lumpur 001` |
| `address` | Fictional address; includes city/state for searching | `Fictional Lot ... (synthetic)` |
| `status` | `Active` or `Inactive` | `Active` |
| `exception` | Boolean flag using `true` or `false` | `false` |

Internal store identities and SUITE Storecodes are generated by the application;
do not add invented internal codes to the import files.

## Walkthrough in the web app

1. Start DataFlow Hub and open **Client**. Create or open a retailer setup.
2. Enter the retailer's name, key, service type, sender email, and optional
   retailer email from `retailers.json`. For Aurora, use
   `dataflow.aurora@example.com` and `retailer.aurora@example.com`; the other
   retailers use the same pattern with their lowercase names. Save the retailer
   before importing stores.
3. In **Store Table Management**, open the bulk store import controls. Choose
   **Add new stores** and select that retailer's matching CSV file.
4. Preview the import. For an empty retailer, expect **300 added, 0 updated,
   0 unchanged and 0 invalid rows**. Nothing should be saved by preview alone.
5. Confirm the import. Verify 300 stores are present and internal store codes
   have been generated.
6. Use search, status filters, sorting and pagination to find stores. Searching
   for `Kuala Lumpur` within one retailer should find 25 stores; filtering all
   stores to Inactive should find 15. Reset search before checking the status
   count, because active search and filters combine.
7. Repeat with each of the other three retailers. Keep their store files separate.
8. Confirm all four retailer store counts are 300, for 1,200 stores overall.

Use the application's downloadable CSV/Excel template when preparing a new file.
These supplied datasets use CSV so they can be inspected without spreadsheet
software; the import feature also supports the Excel template.

## Error and update demonstrations

### Invalid data

Upload `invalid_stores.csv` to any saved retailer and preview it. All five data
rows should be invalid, confirmation should be disabled, and an error report
should be available. CSV line numbers include the header:

| CSV line | Expected issue |
|---:|---|
| 2 | Duplicate store ID; matches line 3 ignoring case |
| 3 | Duplicate store ID; matches line 2 ignoring case |
| 4 | Missing store name |
| 5 | Invalid status (`Unknown`) |
| 6 | Invalid exception value (`maybe`) |

This fixture never intentionally creates a partial import. Correct the file and
preview it again before confirming.

### Updating one existing store

After importing Aurora's 300 stores, upload `aurora_update_existing_store.csv`
with **Add or update matching stores** (`upsert`) selected. The first preview
should show **0 added and 1 updated**. Confirm it and check that
`DEMO_AURORA-001` has the new flagship name/address and Inactive status.
Its internal identity and SUITE Storecode must remain unchanged; the other 299
stores must be unchanged and the retailer must still contain 300 stores.
Repeating the same upsert should report the row as unchanged. This example
updates existing data only; it does not demonstrate adding a 301st store.

## Reproduce the files

From the `data-flow-hub` folder:

```sh
python script/generate_store_demo.py
```

The generator has no random state or dependency on the current date. Re-running
it verifies identical generated contents and leaves them unchanged. It refuses
to overwrite a generated filename whose contents have been edited. To regenerate
into another project-contained folder:

```sh
python script/generate_store_demo.py --output sample_data/store_import_copy
```

It rejects output folders outside `data-flow-hub` and symlink output files. It
does not overwrite this README, connect to PostgreSQL, create retailers, or
modify the application's records.

## Optional additive demo loader

For a convenient local development demo, first inspect the plan from the
`data-flow-hub` folder:

```sh
python script/load_store_demo.py
```

This default command verifies the fixture fingerprints and prints four retailers
with 300 stores each. It does **not** import the app or connect to a database.
With the app's Python virtual environment active and the configured local
PostgreSQL service running, explicitly opt in to loading:

```sh
python script/load_store_demo.py --apply
```

The loader uses the existing Flask API handlers for retailer creation and the
same store-import preview/confirmation flow as the UI. It adds only missing demo
retailers and missing demo stores, preserving previously generated internal IDs
and SUITE Storecodes. Unrelated retailers are left alone.

Before starting changes, it checks all four matching retailer keys
case-insensitively. Existing demo retailer setup values and store details must
match these fixtures; archived retailers, unexpected store keys, or changed store
details cause refusal rather than replacement. For example, running the loader
again after the one-store upsert demonstration will refuse that changed demo
store instead of undoing the user's update.

A complete unchanged rerun performs no imports and consumes no additional store
codes or configuration versions. Each retailer import is atomic, but the four
retailers are not a single global transaction. If an operation fails midway,
previously completed retailers remain saved; correct the problem and rerun to
add only what is still missing. The loader never deletes records to reset a demo.

Fixture fingerprints use the generator's LF line endings. The loader also accepts
Git for Windows CRLF checkouts by normalizing line endings before verification;
all other bytes remain checked. Real content edits still fail verification.
